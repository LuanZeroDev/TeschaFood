# 3.5. Decisión de Backend e Integración

## ¿Por qué no se ven los cambios en el emulador?

No es problema de base de datos. Es que se agregó una dependencia nueva (`play-services-location`) y Gradle necesita sincronizarse antes de compilar. En Android Studio:

1. Debería aparecer el banner amarillo **"Gradle files have changed"** → clic en **Sync Now**
2. Si no aparece: menú **File → Sync Project with Gradle Files**
3. Después: **Run → Run 'app'** (o el botón ▶️)

---

## ¿Firebase es lo óptimo para esta app?

**Depende del caso de uso.** Para una app de delivery tipo Uber Eats, Firebase tiene ventajas reales pero también límites importantes:

| Necesidad | Firebase | Alternativa |
|---|---|---|
| Auth (login/registro) | ✅ Excelente, 5 min de setup | — |
| Real-time (rastreo de pedido) | ✅ Firestore / Realtime DB perfecto | Socket.io en backend propio |
| Push notifications | ✅ FCM es el estándar | — |
| Catálogo de productos | ⚠️ Funciona pero es caro a escala | PostgreSQL + REST API |
| Lógica de negocio (comisiones, pagos) | ❌ No sirve, necesita backend | Node.js / Django / Spring |
| Geofiltrado real | ❌ Firestore no hace queries geoespaciales eficientes | PostGIS + backend propio |

## Recomendación: Arquitectura Híbrida

```
Firebase Auth       → login/registro (mínimo esfuerzo)
Firebase FCM        → notificaciones push
Firestore           → rastreo en tiempo real del pedido (OrderStatus)
Backend propio      → catálogo, pedidos, pagos, geolocalización
```

## Opción óptima: Supabase

**Supabase** es probablemente la opción más óptima para este proyecto porque:

- **PostgreSQL real** → queries geoespaciales con PostGIS para el filtrado por cercanía
- **Auth integrada** → compatible con el flujo que ya construimos
- **Realtime** → para el tracking de pedidos
- **Storage** → para imágenes de productos
- **Gratis** hasta escala significativa
- **SDK de Android** disponible
- **Open-source** / autoalojable
